# ADR 0005: A Document Keeps Its Identity When Its Name Changes

Status: Accepted (design)
Date: 2026-09-10
Amends: [ADR 0004](0004-organization-workspace-folder-and-org-billing.md) in one
place and nothing else — a document's identity is a UID carried in its filename
rather than its path.

**ADR 0001's contract is unchanged.** Upload → branch → pull request → review →
merge → tag is still law. Only what the tag is named after changes.

> **This replaces an earlier version of ADR 0005**, accepted 2026-09-09, which
> made the whole filename a UID, moved the title into a committed sidecar, and
> required the `document_versions` index, an organization webhook and a
> reconciler. That version correctly identified the bug below and then paid far
> too much to fix it. What changed is recorded under
> [What The First Version Got Wrong](#what-the-first-version-got-wrong); the
> problem statement and the rejected alternatives are its work, kept.

## Why This Exists

One function decides more than it looks like it does:

```ts
// packages/utils/documentPath.ts
export function buildDocumentVersionTag(slugPath: string, version: number) {
  return `${slugPath}/v${version}`;
}
```

A document's identity **is** its path. `documentSlugPathFromVersionTag` reads
identity back out of the tag name, `listVersionsByDocument` filters a binder's
tags by that prefix, and `nextVersionFrom` takes the highest of what survives and
adds one. So the version number is a function of the path.

Rename the file and three things happen at once, none of them loudly:

1. **Numbering restarts at v1.** The prefix filter matches nothing, and the next
   publish mints v1 of a policy on its fifth revision.
2. **The old tags orphan.** `nursing/infection-control/v1..v4` still exist and
   still point at real commits, but nothing in the product will list them again,
   because no document has that path any more.
3. **The History tab silently shortens** — the compliance record, the thing a
   surveyor is shown.

The implementation notes already wrote the sentence this deserves, about the
"becomes v1" defect: _a version number is the one thing this product cannot be
casually wrong about._

**There is no cheap escape through git.** Gitea's commits endpoint takes `sha`,
`path`, `since`, `until`, `stat`, `verification`, `files`, `page`, `limit` and
`not`. There is no `follow` — verified against
`services/api/gitea-client/spec/openapi3.json` on 2026-09-10. `git log --follow`
is not reachable through the API, so lineage cannot be recovered after the fact.
It has to be modelled up front.

**The bug is latent today.** There is no rename or move anywhere in the product —
no route, no handler, no UI. Nothing a person can do in Bindersnap triggers it.
That is exactly why this is worth fixing now and cheaply: the first person to
build "retitle a policy" would otherwise break version numbering silently, and
retitling is not an exotic feature. A policy whose title can never be corrected
is not a policy system.

### Why not simply forbid renames

Considered, and genuinely the cheapest answer: freeze the path once a document
has a published version, the way document control freezes a document number.

Rejected, because **the path is also the title.** `name` is the last path segment
(`packages/api-schema/schemas/workspaces.ts`), so freezing the path freezes the
title, and correcting a wrong title is a thing customers will need. The freeze
also buys nothing that this ADR does not, and costs the rename.

## Decision

### 1. A document is a ULID, carried as a segment of its filename

```
nursing/hand-hygiene.01J8XZ4K7MQ9V3B0RN7YHS2E1D.md
```

- Minted at creation, **never derived from the title**, never changed.
- A **ULID, not a UUID**: it appears in every filename and every tag name, and 36
  characters of hyphenated hex is a tax on both. 26 characters, no hyphens to
  confuse a path segment, and it sorts by creation time as a string.
- **Globally unique, not per binder**, so moving a document between binders can
  later be a re-tag rather than a new document.

**Parsing is unambiguous.** `slugifyDocumentName` reduces a title to lower-case
alphanumerics and dashes, so the human half can never contain a dot. The
identity is the last dot-separated segment that satisfies `isDocumentUid`; what
precedes it is the name, what follows it is the extension. A document with no
extension parses the same way.

**The human half is free to change.** Renaming `hand-hygiene` to
`hand-hygiene-and-ppe` leaves the identity segment untouched, so the tags still
match and the numbering continues. That is the entire fix.

### 2. The folder stays in the path, because CODEOWNERS is path-matched

Flattening to `documents/<uid>.pdf` and making the folder metadata was the
obvious simplification. It is not available.

Per-folder sign-off is `.gitea/CODEOWNERS`, generated by
`packages/utils/codeowners.ts`, and Gitea matches its anchored regexes **against
the changed file paths** at pull request time. With no folder in the path, "the
infection control group signs off on anything in `nursing`" cannot be written
down at all — and there is deliberately no `folder_approvers` table to fall back
on, because a table would shadow a git object Gitea enforces at merge time.

CODEOWNERS patterns match folders, never filenames, so nothing in this ADR
touches them.

### 3. Version tags are `<uid>/vN`

`nursing/infection-control/v4` becomes `01J8XZ4K7MQ9V3B0RN7YHS2E1D/v4`.

That is a real loss of legibility in `git tag -l`, and it is paid back in the tag
message, which already carries the policy stamp from
`services/api/version-stamp.ts`. The stamp gains two fields — **the title as
published** and **the path as filed** — so a version stays readable exactly where
readability was the point, a person running `git tag -n1` on a bare clone in five
years:

```
01J8XZ4K7M…   Hand Hygiene and PPE v4 — nursing/hand-hygiene-and-ppe.01J8XZ4K7M….md
```

Both are point-in-time facts that became unrecoverable from the tag name, which
is precisely what makes them worth stamping. Nothing reads them back — the same
rule as the rest of the stamp, because a format nothing parses cannot drift out
of step with a parser.

**The tag is also the counter, and that is a feature.** Two changes publishing
the same document at once both compute v4 and both try to create
`<uid>/v4`; git refuses the second, atomically and for free. A counter in SQLite
needs a transaction and a lock to get the same guarantee, and the failure mode
when it does not have one is two documents both called v4. A version number in a
committed file is worse still: both changes merge cleanly and the conflict is
silent. This is the strongest argument for tags and the first version of this ADR
did not make it.

### 4. The title stays the filename, for now

A title is evidence — a fact a surveyor can ask us to prove — and the filename
already satisfies that test. The tree at each version's tag records what the
document was called when that version was approved, so "show me the title in
force in March 2025" is answered by reading the tree at that tag. It is in git,
it is at a ref, and it has history.

What the filename cannot carry is **casing and punctuation**: a slug renders
`hipaa-training-policy` as "Hipaa Training Policy", which
`apps/app/documentDisplay.ts` currently papers over with a list of known
initialisms, and says in its own comment that it is a stopgap. That is a real
problem and it is **not this one**. Fixing it means storing the title a person
typed, which is worth doing deliberately rather than smuggling into a change
about identity.

When it is done, the natural home is a sidecar keyed by the UID — and this ADR is
deliberately shaped so that adding one later is additive, not a migration.

### 5. No index, no sidecar, no webhook, no reconciler

None of them are needed for this, and the measurement that said so still stands.

`readBinderDocuments` reads a binder in **three calls**: the tree listing, the
open pull requests, and the binder's tags. `listVersionsByDocument` walks the
tags once and groups them. Keying the grouping on the UID instead of on the path
is a like-for-like swap — **the tree listing already returns filenames, so it
already returns the UIDs.** No read is added anywhere.

The first version of this ADR needed the `document_versions` index because it
moved the title into a sidecar, which is one Gitea call per document on a
listing. Leave the title in the filename and that cost never appears, so the
index goes back to being what the implementation notes measured it to be: an
optimization with no latency problem to solve. The three conditions ADR 0004 put
on it are unchanged and still binding if it is ever built.

## What The First Version Got Wrong

Recorded because the reasoning is worth keeping, not to score a point against it.

- **It conflated "identity must be stable" with "identity must be the
  filename."** Only the first is required. Once the UID is a _segment_, the
  human name survives, and with it `ls`, `grep`, Gitea's file browser, and
  `readLibrary`'s search — which filters on `row.name` and `row.slugPath`
  (`services/api/server.ts`) and would have matched nothing against bare ULIDs.
- **It made the title a sidecar, and the sidecar forced everything else.** Two
  files per document, a pairing invariant enforced at create, move, delete and
  publish, one read per document on a listing, and therefore an index, and
  therefore a webhook to fill it, a reconciler to repair it and a watermark to
  make the repair cheap. Four new subsystems, all downstream of one decision that
  the rename bug never required.
- **It justified tags by durability alone** and missed the stronger argument,
  that git enforces uniqueness on a ref.

## Assumption This Rests On

**Nobody edits these repositories outside Bindersnap.** The product owner's
position, recorded 2026-09-10: customers do not know Gitea is there and its web
interface is being removed.

That is what makes a reconciler unnecessary. A rename made directly in Gitea
would still strand a document's history, because a file whose identity segment
was stripped by hand is a document the product can no longer recognise.

If that assumption stops holding, the repair is not a reconciler but a check:
every tag `<uid>/vN` whose UID matches no document on `main` is a stranded
version, and both inputs — the tag list and the tree listing — are already in
hand in `readBinderDocuments`. It is a set difference over data already fetched,
and it can be added the day it is needed.

## What This Costs, Honestly

- **Filenames carry a 26-character blob.** `hand-hygiene.01J8XZ4K7M….md` is
  uglier than `hand-hygiene.md`, in the repository and in the branch names that
  embed the document slug. This is the price, and it buys back everything the
  first version of this ADR was going to spend.
- **A file renamed without its identity segment is a document we cannot
  recognise.** Publish refuses one, loudly. Degrading quietly is the exact
  failure ADR 0004 names twice — the old config parser falling back to the
  permissive policy, and Gitea's own CODEOWNERS parser dropping a line it cannot
  compile.
- **`git tag -l` stops being readable.** `git tag -n1` still names every version,
  its title and its path, which is what a person actually reads.
- **The display-title problem is untouched.** "Hipaa Training Policy" is still
  wrong, and still papered over by an initialism list.

## Migration

Following the decisions taken 2026-09-04 — no real customers, the seed is the
fresh start, no compatibility window — **there is no backfill.** Binders built
under `<slugPath>/vN` are rebuilt by the seed.

If that assumption has changed by the time this is built, it is a `human-needed`
issue and not a judgment call for the implementer: re-tagging published versions
rewrites evidence, and evidence is not ours to rewrite.

## What Is Left

In dependency order. None of it is built.

1. **UID minting**, and the filename shape, with parsing that tolerates a missing
   extension.
2. **`buildDocumentVersionTag` keyed on the UID**, and the tag grouping in
   `listVersionsByDocument` with it.
3. **The publish guard** that refuses a content file with no valid identity
   segment.
4. **The title and path in the version stamp.**
5. **The seed**, regenerated.

## Open Questions

1. **Does a document keep its UID when it moves between binders?** This ADR says
   the UID is globally unique so that it can. Tags are per repository, so one
   UID's history would span two of them, and the audit packet would have to know
   that. Moving between binders is not built, and this is not decided.
2. **What else eventually belongs beside a document?** Title and description are
   the candidates, and each is a fact to re-test against ADR 0004's three
   questions rather than to add by default.
