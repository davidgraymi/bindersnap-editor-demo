# ADR 0005: A Document Is a UID, Its Title Is Evidence, and the Version Index Has to Exist

Status: Accepted (design)  
Date: 2026-09-09  
Amends: [ADR 0004](0004-organization-workspace-folder-and-org-billing.md) in two
places and nothing else — a document's identity is a UID rather than its path, and
the `document_versions` index, measured and deliberately deferred, now has to exist.

**ADR 0001's contract is unchanged.** Upload → branch → pull request → review →
merge → tag is still law. Only the name of the thing being tagged changes.

## Why This Exists

One function decides more than it looks like it does:

```ts
// packages/utils/documentPath.ts
export function buildDocumentVersionTag(slugPath: string, version: number) {
  return `${slugPath}/v${version}`;
}
```

A document's identity **is** its path. `documentSlugPathFromVersionTag` reads
identity back out of the tag name, `listVersionsByDocument` filters a binder's tags
by that prefix, and `nextVersionFrom` counts what survives the filter. So the
version number is a function of the path.

Rename the file and three things happen at once, none of them loudly:

1. **Numbering restarts at v1.** The prefix filter matches nothing, and the next
   publish mints v1 of a policy on its fifth revision.
2. **The old tags orphan.** `nursing/infection-control/v1..v4` still exist and still
   point at real commits, but nothing in the product will list them again, because
   no document has that path any more.
3. **The History tab silently shortens** — the compliance record, the thing a
   surveyor is shown.

The implementation notes already wrote the sentence this deserves, about the
"becomes v1" defect: _a version number is the one thing this product cannot be
casually wrong about._ This is the same defect with a rename as the trigger
instead of a migration, and it is worse, because a customer causes it.

There is no cheap escape through git. Gitea's commits endpoint takes `sha`, `path`,
`since`, `until`, `stat`, `verification`, `files`, `page`, `limit` and `not`.
**There is no `follow`.** `git log --follow` is not reachable through the API, so
lineage cannot be recovered after the fact. It has to be modelled up front.

### Why not simply forbid renames

Considered, and genuinely the cheapest answer: freeze the path once a document has
a published version, the way document control freezes a document number.

Rejected, because **the path is also the title.** `name` is the last path segment
(`packages/api-schema/schemas/workspaces.ts`), so freezing the path freezes the
title, and a policy whose title can never be corrected is not a policy system.
Fixing that needs a title separate from the path, which is most of this ADR. The
freeze then buys nothing and still costs the rename.

## Decision

Five parts. The first is the one the rest follow from.

### 1. A document is a UID. Its path is where it is filed.

```
nursing/01J8XZ4K7MQ9V3B0RN7YHS2E1D.pdf     content
nursing/01J8XZ4K7MQ9V3B0RN7YHS2E1D.json    title, description
tag 01J8XZ4K7MQ9V3B0RN7YHS2E1D/v4          -> the merge commit that published it
```

- Minted at creation, **never derived from the title**, never changed.
- Short and sortable — a ULID, not a raw UUID. It appears in every path, every tag
  name and every URL, and 36 characters of hyphenated hex is a tax on all three.
- **Globally unique, not per binder.** Moving a document between binders is then a
  re-tag rather than a new document, and binder-to-binder moves are foreseeable.
- The extension stays on the content file. It is how we know how to render it.

### 2. The folder stays in the path, because CODEOWNERS is path-matched

Flattening to `documents/<uid>.pdf` and making the folder metadata was the obvious
simplification. It is not available.

Per-folder sign-off is `.gitea/CODEOWNERS`, generated by `packages/utils/codeowners.ts`,
and Gitea matches its anchored regexes **against the changed file paths** at pull
request time, refusing the merge under `block_on_codeowner_reviews` on 28.0.0. With
no folder in the path, "the Infection Control group signs off on anything in
`nursing`" cannot be written down at all — and there is deliberately no
`folder_approvers` table to fall back on, because a table would shadow a git object
Gitea enforces at merge time.

So the folder is load-bearing, and the operations fall out of it:

| Operation | In git               | Version continuity | Who signs off       |
| --------- | -------------------- | ------------------ | ------------------- |
| Retitle   | sidecar edit only    | untouched          | the folder it is in |
| Move      | rename the pair      | untouched          | **both** folders    |
| Publish   | tag the merge commit | +1                 | per CODEOWNERS      |

A move lands in two folders' paths, so both folders' owners sign off. That is
correct, and it is free.

This also settles a framing question raised while deciding: **the binder is not an
index.** It is the unit of governance — the repository holding CODEOWNERS, branch
protection and the teams. Folders as metadata would demote it to an index and take
the enforcement mechanism with them.

### 3. The title is evidence, so it lives in git and changing it is a change

Run it through ADR 0004's second question — a fact about what happened that a
surveyor could ask us to prove, where "our database says so" is not an acceptable
answer. A title passes it twice:

- "Show me the hand hygiene policy in force in March 2025" cannot be answered from
  a mutable SQLite string with no history.
- Retitling "Hand Hygiene" to "Hand Hygiene and PPE" **changes what the document
  claims to cover.** Outside a change request, the scope of a controlled document
  moved and nobody approved it.

So a title is mutable, but not without review and not without history. It lives in
a committed sidecar, `<folder>/<uid>.json`, changed in the same commit as the
content it describes, reviewed in the same change, readable at any ref. That last
property is the only reason to be in git at all — the same argument ADR 0004 used
to _remove_ `.bindersnap/config.json`, pointing the other way because this is
evidence and that was configuration.

Three placements were rejected:

- **SQLite.** Fails the point-in-time test above.
- **A single binder manifest** (`.bindersnap/documents.json`). One read serves a
  whole listing, and one file is the conflict surface for every concurrent change.
  Two people adding documents on separate branches collide.
- **The markdown H1.** Absent from a PDF or a `.docx`, and two sources of truth for
  a title is the disagreement least worth having. The editor keeps the H1 in step
  with the sidecar; the sidecar wins.

The sidecar and its content file are **a pair** — created, moved and deleted in the
same commit. Publish refuses a document missing either half, **loudly**. A content
file with no sidecar is a document with no name, and degrading quietly is the exact
failure ADR 0004 names twice: the old config parser falling back to the permissive
policy, and Gitea's own CODEOWNERS parser dropping a line it cannot compile.

### 4. Version tags are `<uid>/vN`, and the tag message carries the title

`nursing/infection-control/v4` becomes `01J8XZ4K7MQ9V3B0RN7YHS2E1D/v4`.

That is a real loss of legibility, and it is paid back in the tag message, which
already carries the policy stamp from `services/api/version-stamp.ts`. The title
goes on the summary line, so a version stays readable exactly where readability was
the point — a person running `git tag -n1` on a bare clone in five years:

```
01J8XZ4K7M…   Hand Hygiene and PPE v4 — nursing/01J8XZ4K7M….pdf
```

The stamp gains two fields: **the title as published** and **the path as filed**.
Both are point-in-time facts, and both became unrecoverable from the tag name,
which is precisely what makes them worth stamping. Nothing reads them back — the
same rule as the rest of the stamp, because a format nothing parses cannot drift
out of step with a parser.

### 5. The index is refreshed from Gitea, never written through

ADR 0004 specified `document_versions` and its three conditions. The implementation
notes then measured the tag walk, found no latency problem worth a second source of
truth, and did not build it.

**This ADR reopens that**, for a reason the measurement did not have: a listing now
needs a **title per document**, and titles are in sidecars. One sidecar per document
at page load is one Gitea call per document — the cost profile the binder model was
built to escape. The index stops being an optimization of a fast path and becomes
the way a listing is affordable at all.

The three conditions are unchanged and still binding. **The index serves browsing;
Gitea serves proving.**

## How The Index Is Built

**One function.** `refreshBinder(org, repo)` reads Gitea — walks the tags, reads the
tree on `main`, reads the sidecars, joins the closed changes — and upserts that
binder's rows. It is the only thing that writes the index. Four triggers call it:

| Trigger                                   | Job                            | Latency   |
| ----------------------------------------- | ------------------------------ | --------- |
| Gitea webhook                             | the normal path                | seconds   |
| the publish handler, after Gitea confirms | read-your-writes               | immediate |
| the reconciler, on a timer                | repair                         | minutes   |
| full rebuild, input is Gitea only         | condition 1, migration, and DR | on demand |

### Why not write-through

- **Two writes, no transaction across them.** Gitea succeeds, SQLite fails, and a
  row claims v5 while git has v4. Wrong in the dangerous direction, and nothing
  detects it.
- **It only sees writes that went through the BFF.** Gitea is a real Gitea with its
  own UI. Merge a change there, push a tag by hand, let an admin act directly, and
  the index diverges silently. The premise of the product is that Gitea is the
  source of truth and we are one of its clients.
- **There is no repair path.** A missed write is permanent, which makes the index a
  source of truth by accident and breaks condition 3.

> **Every index write is the product of a read from Gitea, never of what a handler
> believes it just did.**

The publish handler may _trigger_ a refresh. It may not write a row. That is the
line ADR 0004's second condition is drawing, and it decides every future case.

### The webhook is a trigger, not data

Do not apply the payload. Gitea delivers at least once, in no guaranteed order, and
applying payloads means a parser and an ordering rule per event shape. Using an
event only as "this binder changed, go read it" collapses duplicate, out-of-order
and missed delivery into one behaviour: a redundant read.

Consequences worth having:

- **Idempotency stops being a correctness problem.** A duplicate delivery costs one
  wasted read. Dedupe by delivery id if the saving is worth it, following
  `processed_webhook_events` — an optimization now, not a guard.
- **Coalesce instead.** A burst of events for one binder debounces to one refresh.
- **Register at the organization level.** `POST /orgs/{org}/hooks`, subscribing to
  `push`, `create`, `delete`, `pull_request` and `repository`. A new binder is then
  covered with no per-repository provisioning step that can fail, and the reconciler
  covers an organization whose hook never registered.
- **The route carries no session,** so it verifies an HMAC against the secret set
  when the hook was registered.

### Two details that keep a refresh cheap

- **A watermark per binder:** the head commit of `main` and the tag count. Two small
  calls say whether anything moved, and the full walk only runs when they disagree
  with what is stored.
- **Skip unchanged sidecars.** The tree listing returns a blob SHA per file, so a
  refresh fetches only the sidecars whose SHA differs from the stored one. A binder
  where one policy changed costs one extra read, not two hundred.

Rows stay keyed on **immutable git coordinates** — tag name and commit SHA — so a
row is either correct or detectably stale, never subtly wrong.

## What This Costs, Honestly

- **A bare clone is no longer readable at `ls`.** Folders still are, and `git tag -n1`
  still names every version and its path. That is most of what a reader needs, and
  it is the price of an identity that survives a rename.
- **Two files per document instead of one.** Every create, move and delete moves the
  pair, and publish verifies it.
- **Browsing gains a background job,** a webhook route and a reconciler that did not
  exist. The index is still droppable: without it a listing reads git and is slow,
  not wrong.
- **Listings are eventually consistent.** A change made directly in Gitea can be
  seconds stale in the app. Acceptable exactly because nothing that gates a decision
  reads the index — the publish gate, the approval check and the audit packet read
  Gitea.
- **URLs become UID-shaped:** `/{org}/{binder}/{uid}`. Uglier, and it quietly solves
  the rename-and-redirect problem the implementation notes deferred, because the
  address stops moving when the title does.

## Migration

Following the decisions taken 2026-09-04 — no real customers, the seed is the fresh
start, no compatibility window — **there is no backfill.** Binders built under
`<slugPath>/vN` are rebuilt by the seed.

If that assumption has changed by the time this is built, it is a `human-needed`
issue and not a judgment call for the implementer: re-tagging published versions
rewrites evidence, and evidence is not ours to rewrite.

## What Is Left

In dependency order. None of it is built.

1. **UID minting and the sidecar**, with the pair enforced at create, move, delete
   and publish.
2. **The title in the version stamp**, and `buildDocumentVersionTag` keyed on the UID.
3. **`refreshBinder`, the table, and the full rebuild.** Build the rebuild first: it
   is the definition of correct, and every other trigger is an optimization of it.
4. **The organization webhook**, its HMAC route, and registration at organization
   creation.
5. **The reconciler**, with the watermark.
6. **UID URLs**, and the listings moved onto the index.

## Open Questions

1. **Does a document keep its UID when it moves between binders?** This ADR says
   yes, which makes the move a re-tag. It also means one UID's history spans two
   repositories, and the audit packet has to know that.
2. **What else belongs in the sidecar?** Title and description are the minimum.
   Owner, review cadence and department are candidates, and each is a fact to
   re-test against ADR 0004's three questions rather than to add by default.
3. **Should the reconciler detect tags the app did not write?** A tag pushed by hand
   matching `<uid>/vN` is currently indistinguishable from one we minted.
