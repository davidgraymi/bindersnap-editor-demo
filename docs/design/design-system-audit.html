Design System Audit · 28 Aug 2026

A strong token layer with no floors built on top of it

Bindersnap's token architecture is better than most systems this size — two clean layers, real dark mode, 99% colour adoption. Everything above the tokens is missing: the component primitives exist but nobody uses them, the documentation describes tokens that were deleted, and nothing in CI stops any of it from drifting further.

Baseline

What's already right

Worth stating plainly before the findings, because these are the parts you should not touch while fixing the rest.

  • The two-layer split is the correct architecture. --bs-* semantic tokens flip with the theme; --brand-* tokens never do. The file states the rule and the codebase mostly follows it.
  • Colour adoption is near-total. Across 12,629 lines of CSS there are 34 hardcoded hex values and 27 raw rgba() — and almost all of them cluster into one cause (below), not scattered sloppiness.
  • Dark mode is designed, not inverted. Four warm-ink surface steps mirroring the paper steps, a cream text ramp, stronger tints, higher-opacity shadows. Only 15 [data-theme="dark"] component overrides are needed in the whole app — the token layer absorbs the rest.
  • The three-font stack is enforced in practice. Lora / Geist / Geist Mono, loaded once, used by role. No drift into a fourth face.
  • prefers-reduced-motion is handled in both the app and landing stylesheets.

The type and spacing gaps are not discipline problems — they're scale problems. The scales were designed for a marketing page and never extended for dense product UI. There is no step between 0.75rem (12px) and 0.875rem (14px), so 13px gets typed by hand 24 times. Spacing starts at 4px, so 2px and 6px get typed by hand 46 times.

Findings

Ten things to fix, in the order I'd fix them

Ranked by damage-per-hour, not by size. The first three are half a day of work between them.

Critical

1  ·  The palette has two hues; the product needs six

~2h

The system defines coral and green. The app also needs to say needs review, waiting, informational, and destructive — and every one of those is a hardcoded literal: amber #d97706/#b45309, blue #1d4ed8/#3b82f6, violet #7c3aed, teal #0f766e. That accounts for nearly all 61 colour literals in the codebase.

Because they're literals, they don't flip with the theme — which makes this an accessibility bug, not just a tidiness one. Measured against the dark surface they sit on:

Component Foreground Light Dark
.vault-triage-pill--active-waiting #1d4ed8 5.96 ✓ 2.02 ✕
.rev-avatar--tone1 #1d4ed8 5.72 ✓ 2.15 ✕
.vault-triage-pill--active-needs-review #b45309 4.29 ✓ 2.46 ✕
.rev-avatar--tone2 #7c3aed 4.91 ✓ 2.49 ✕
.vault-status-review #b45309 4.42 ✓ 2.56 ✕
document status teal #0f766e 4.75 ✓ 2.57 ✕
.rev-avatar--tone4 #b45309 4.39 ✓ 2.76 ✕

Seven for seven. Every hardcoded status colour passes AA in light mode and fails it in dark, and the triage pills — the primary signal on the dashboard — are the worst of them at 2.02:1.

Fix Add a semantic status family as --bs-* triads so they flip. This page uses the proposed ramp for its own severity chips — the amber and coral you're reading are the light/dark pairs below. 
/* :root — light */
--bs-status-warn-fg:     #8f5e02;   /* needs review     */
--bs-status-warn-bg:     rgba(143, 94, 2, 0.10);
--bs-status-warn-border: rgba(143, 94, 2, 0.22);
--bs-status-info-fg:     #1d4ed8;   /* waiting          */
--bs-status-danger-fg:   #c94d1a;   /* changes / declined */
--bs-status-ok-fg:       #15803d;   /* approved         */

/* [data-theme="dark"] — lift the hue, keep the meaning */
--bs-status-warn-fg:     #fbbf24;   /* 2.46 → 6.78 */
--bs-status-info-fg:     #93c5fd;   /* 2.02 → 6.50 */
--bs-status-danger-fg:   #fb8c5a;   /* 3.29 → 4.99 */
--bs-status-ok-fg:       #4ade80;   /* 4.60 → 6.78 */
Then delete the seven [data-theme="dark"] component overrides that exist only to patch this.
Critical

2  ·  AGENTS.md tells agents to use tokens that don't exist

~45m

The frontend rules instruct: "Use --color-*, --font-*, --space-*, --radius-*, --shadow-*." Three of those five families are not defined anywhere. --space-4, --radius-md and --text-h1 all resolve to nothing. The real names are --brand-space-4, --brand-radius-md, --brand-text-h1.

The AGENTS.md token reference block is the v1 vocabulary; the file is v2. Any agent that follows the documentation writes CSS that silently doesn't apply — and you have four agent definitions in .claude/ reading it.

Fix Rewrite the "Key token categories" block in AGENTS.md against the actual file, and change the rule to "use --bs-* for anything theme-reactive, --brand-* for anything fixed." That sentence is the system's single most important rule and it currently appears only as a comment inside the CSS.
Critical

3  ·  The contrast table in the token file is wrong

~20m

bindersnap-tokens.css:219 claims "Contrast ratios verified at WCAG AA for all text levels." Three of the four rows are inaccurate, and one of them is a failure being reported as a pass.

Token File claims Actual (on #fafaf7) Verdict
--bs-text-primary 13.2 16.72 understated
--bs-text-secondary 9.4 9.82 close
--bs-text-muted 5.1 4.59 still AA, but overstated
--bs-text-faint 3.1 2.41 fails even large-text AA (3.0)

--bs-text-faint is also asymmetric between themes — 2.41:1 in light, 3.65:1 in dark. It's used for input placeholders, which is exactly where it matters.

Fix Darken light-mode --bs-text-faint from #a8a29e to about #96908a (3.02:1), correct the four numbers in the comment, and add the source of truth — a unit test that recomputes them, so the comment can never drift again.

5  ·  The primitives have no states

~3h
Primitive Default Hover Focus Disabled Loading Error Sizes
.bs-btn ✓ ✓ ✕ ✕ ✕ — ✕
.bs-input ✓ ✕ ✓ ✕ — ✕ ✕
.bs-card ✓ ✓ ✕ — — — ✕
.bs-email-row ✓ ✓ ✓ ✕ ✕ ✕ —

.bs-btn has no :focus-visible at all — the whole token file has zero. Across the app there are 67 :hover rules against 31 :focus-visible, so roughly half of what responds to a mouse is invisible to a keyboard. There is no destructive variant, so "Remove collaborator" and "Publish" look the same.

Fix .bs-btn:focus-visible, :disabled, --sm/--lg, --danger, and an [aria-busy] spinner state — one block, and it raises the floor for all 71 existing call sites at once.
High

6  ·  Nothing enforces any of this

~2h

There is no stylelint config, no CSS test, and Prettier only checks formatting. Every finding on this page is free to regress the day after it's fixed. You already treat TypeScript strict mode as the linter — the stylesheets have no equivalent.

Fix A packages/ui-tokens/tokens.test.ts that parses the CSS and asserts four things, runnable under bun run test:app with no new dependency: 
1. no hex or rgba() literal outside bindersnap-tokens.css
2. every var(--…) reference resolves to a defined token
3. every defined token is referenced at least once
4. computed contrast for each text token meets its documented ratio
Rule 4 makes finding 3 permanently unrepeatable. Rule 1 needs an allow-list for the handful of intentionally-fixed values (#000 on the blend-mode comparison, .bs-btn-dark).

~30m

Medium

9  ·  Two implementations of the same landing primitives

~2h

bindersnap-tokens.css defines .bs-reveal, .bs-reveal-d1…d4 and .bs-compare-item. bindersnap-landing.css defines .reveal, .reveal-d1…d3 and .compare-item — the same components, unprefixed. index.html uses the unprefixed ones exclusively, so the .bs-* versions are dead weight shipped on every page load.

Of the 21 primitives I checked, 5 are used anywhere and 16 are used nowhere: bs-pill, bs-body, bs-h1–h3, bs-display, bs-container, bs-section, bs-code, bs-file-chip, bs-email-row, bs-nav-badge, bs-compare-item, bs-accent, bs-theme-toggle and the reveal family all score zero.

Fix Pick one. Either adopt the bs- prefix in index.html and delete the landing twins, or delete the unused half of the token file's component section and stop calling it a system. The second is more honest for a solo codebase and is what I'd do — keep .bs-btn, .bs-card, .bs-input, .bs-eyebrow, .bs-label, add .bs-status, drop the rest.
Medium

10  ·  A 2,381-line page stylesheet lives inside ui-tokens

~30m

packages/ui-tokens/ is described in AGENTS.md as "CSS design tokens, fonts, icons," but 73% of its CSS is bindersnap-landing.css — page-specific styling for one route of one app. It also has no package.json, so consumers reach it by relative path (../../packages/ui-tokens/css/index.css) rather than through the @ui/* alias the repo otherwise uses.

Fix Move bindersnap-landing.css to apps/app/landing.css next to the component it styles, and give ui-tokens a package.json with a ./css export. The package then contains only things that are genuinely shared.

Extend

Four token families the system is missing

These aren't cleanup — they're new vocabulary the product has already proven it needs, because it's been writing the values by hand.

A dense UI type ramp

The nine-step scale runs from --brand-text-label (11px) to --brand-text-display, with nothing designed for tables, chips, and metadata rows. The evidence is 149 hand-typed sizes across 19 values — including five half-pixel values (10.5, 11.5, 12.5, 13.5, 14.5px) that exist only because there was no correct step to reach for. 

/* Fills the gap between --brand-text-xs (12px) and --brand-text-sm (14px) */
--brand-text-ui-xs: 0.6875rem;  /* 11px   — replaces 23 hand-typed */
--brand-text-ui-sm: 0.75rem;    /* 12px   — replaces 14 + 18 at 12.5 */
--brand-text-ui-md: 0.8125rem;  /* 13px   — replaces 24 + 7 at 13.5 */
--brand-text-ui-lg: 0.875rem;   /* 14px   — already exists as -sm */

Micro-spacing

The base-8 scale starts at 4px. The three most common raw spacing values in the app are 2px (24×), 3px (22×) and 6px (20×) — sub-step gaps inside chips, icon rows, and inline stacks. AGENTS.md forbids off-scale values, so today the rule is broken 274 times because following it is impossible. 

--brand-space-0-5: 2px;   /* icon-to-label, chip internals */
--brand-space-1-5: 6px;   /* inline stacks                 */
--brand-space-2-5: 10px;  /* dense row padding             */

That's 3 steps absorbing roughly 70 of the 274 violations. Either add them, or amend the rule in AGENTS.md to say the scale is base-8 above 12px and free below — but pick one, because right now the documentation and the code disagree.

Icon sizing

Lucide icons are sized per call site with no tokens: 8 distinct sizes and 9 distinct stroke widths, including 1.4, 1.5, 1.6, 1.7, 1.75, 1.8, 2, 2.2 and 2.5 — differences no one can see but which guarantee two icons side by side never quite match. 

--brand-icon-xs: 12px;  --brand-icon-sm: 14px;
--brand-icon-md: 16px;  --brand-icon-lg: 20px;
--brand-icon-stroke:      1.5;   /* default — already the plurality */
--brand-icon-stroke-heavy: 2;     /* emphasis only                  */

Best expressed as an <Icon> wrapper around lucide-react that takes size="sm" rather than size={14}, so the tokens can't be bypassed.

Elevation and motion, stated as roles

Four shadow steps and four transition durations exist, but nothing says which belongs to what. A card, a dropdown and a modal each pick a shadow by feel. Name them by role (--bs-elevation-card, --bs-elevation-menu, --bs-elevation-modal) and the choice stops being a judgement call — and the same for the seven raw z-index values still sitting outside the --brand-z-* scale.

Sequence

If you only do one afternoon of this

Findings 1, 2, 3 and 6, in that order. The status ramp removes almost every hardcoded colour and fixes seven dark-mode contrast failures at once. Correcting AGENTS.md stops agents generating new violations while you fix the old ones. The contrast table takes twenty minutes. And the token test makes all three permanent instead of a snapshot.

Findings 4 and 5 — the badge and button consolidation — are the largest and the most deferrable. They're worth doing before the next feature that needs a new status, not before the next release.
