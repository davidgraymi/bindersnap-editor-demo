# Passages are cheap; embedding them is not

Indexing one FTS5 row per passage is **not** much more expensive than one row per document: in a benchmark run for this research (Apple M1, synthetic 3,000-word policies, ~70 passages each), the passage index was **1.40× the document index** and the whole database with text stored **1.15×**, build CPU was 1.25–1.55× and a one-document republish cost ~1 ms against ~0.4 ms. The cost that does grow is query CPU when a common word is ranked across the whole deployment (2.5–3.7× slower), and that is fixed by scoping every query to one organization's rowid block, which ADR 0007 already lists as Amber's first fix and which this analysis says should be built from day one. Semantic search is a different matter. Embedding at passage grain means 0.7M–7M vectors and is ruled out on this host at every scale studied; embedding **heading-aware sections of ≤512 tokens (~8–10 per document)** with a 384-dimension model is affordable: ~0.1–1.2 GB of float32 vectors, an estimated 150–300 MB of RAM for a sidecar model, and pennies-to-$11 of burst CPU credits. Its real limit is time: an on-host backfill of a bge-small-class model takes an estimated **7–17 hours at 10k documents, 17–43 hours at 25k and 3–7 days at 100k**, on both vCPUs, which collides with ADR 0004's "rebuildable" promise long before it collides with RAM or disk. Off-host, Amazon Bedrock's Titan Text Embeddings V2 does the whole 100k corpus for about **$10**, adds no new subprocessor (AWS already is one), and is the recommended path if and when a labelled query set shows that semantic search beats BM25 plus the healthcare synonym list ADR 0007 already plans. Every Graviton figure here is an estimate; the benchmarks that must replace them are listed at the end.

## Passage rows cost 1.4× the index, not 70×

The fear that 70 rows per document means 70× the index misreads how FTS5 stores data. FTS5 keeps a doclist per term: for each row containing the term, a rowid delta and a position list ([SQLite FTS5 §9](https://www.sqlite.org/fts5.html)). Size therefore tracks token occurrences, which do not change when a document is split, plus (term, row) pairs, which do. The benchmark fitted **~1.87 bytes per token occurrence and ~1.51 bytes per (term, row) pair**; splitting a document into passages raised pairs only 2.3× (a 3,000-word policy has ~1,090 distinct terms, its passages ~2,500 summed), plus ~11 bytes per row in `%_docsize` and ~12 in `%_content`. The result scaled linearly from 0.7M to 7M passage rows within 2%.

| Documents | Plain text | Document index | Passage index | Document file (text stored) | Passage file (text stored) |
| --------- | ---------- | -------------- | ------------- | --------------------------- | -------------------------- |
| 10,000    | 169 MiB    | 70 MiB         | 98 MiB        | 248 MiB                     | 284 MiB                    |
| 25,000    | 424 MiB    | 174 MiB        | 244 MiB       | 618 MiB                     | 708 MiB                    |
| 100,000   | 1,694 MiB  | 691 MiB        | 972 MiB       | 2,469 MiB                   | 2,830 MiB                  |

_Measured on M1, `detail=full`, unicode61, one indexed column, after optimize and VACUUM. Synthetic corpus._

These ratios agree with SQLite's own measurement on email, where a `detail=full` index was 45% of the input and `detail=column` and `detail=none` 21% and 8% ([SQLite FTS5, detail option](https://www.sqlite.org/fts5.html)); the benchmark's document design came out at 41/20/7%. Two options flip the conclusion and should be avoided for a passage table: `detail=column` or `detail=none` drop the positions both designs share and leave only the per-pair cost the passage design multiplies, making it **2.8–3.8× larger**, and they also forbid phrase and NEAR queries. A second indexed column costs ~30% (every entry pays a column marker), so titles belong in their own small table, not repeated on 70 passage rows. The porter stemmer ADR 0007 wants saves ~7%, a prefix index for type-ahead adds ~31% ([Mozilla ADR 0008](https://searchfox.org/mozilla-mobile/source/application-services/docs/adr/0008-fts-prefix-config.md)), and the trigram tokenizer for typo tolerance costs **5.3×** unicode61.

The measurements also correct ADR 0007's own sizing. The ADR assumes ~50 KB per document and "about 1 million passages, an index under 1 GB" at 10,000 documents (`docs/adr/0007-search.md`, "How Far This Goes"). Measured, the passage file is ~29 KB per document with text stored, 703k passages and 284 MiB at 10k; even 100k documents is 2.8 GiB, under 10% of the 30 GB gp3 root volume. Real policies, with longer repetitive paragraphs but also short headings, should land at 1.3–1.5× for the index and 1.1–1.2× for the file. Disk is not where any threshold lives. ADR 0007 also keeps `search.db` out of Litestream, so the WAL-replication cost of an occasional `optimize` (which rewrites the whole index and reclaimed only 1–3% here) does not arise; skip `optimize` anyway, because automerge keeps segment counts low by default ([SQLite FTS5 §6](https://www.sqlite.org/fts5.html)).

## Query CPU is the one real cost, and organization scoping erases it

`ORDER BY rank LIMIT 10` must compute bm25 for every matching row before it knows the top ten ([fts5_aux.c](https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_aux.c)), so latency is roughly matching rows × 1.2–1.6 µs (document rows) or ~2.3 µs (passage rows) on an M1. A common word matches 2.5× more passages than documents, which is where the passage design hurts.

| Query, M1 measured             | 10k doc / passage | 25k doc / passage | 100k doc / passage |
| ------------------------------ | ----------------- | ----------------- | ------------------ |
| Term in 90% of documents       | 9.9 / 49 ms       | 32 / 133 ms       | 147 / 542 ms       |
| Term in 50%                    | 7.7 / 15 ms       | 21 / 43 ms        | 60 / 172 ms        |
| Term in 5%                     | 0.7 / 1.1 ms      | 2.1 / 3.0 ms      | 6.4 / 18 ms        |
| Two-term AND                   | —                 | —                 | 4.8 / 2.5 ms       |
| Scoped to a 1,000-document org | —                 | 1.8 / 5.2 ms      | —                  |
| Scoped to a 5,000-document org | —                 | 6.2 / 30 ms       | —                  |

Apply an **estimated, unmeasured** 1.5–2.5× slowdown for one Graviton2 core and the unscoped passage design crosses ADR 0007's Amber line (p95 over 200 ms) at about **25,000 documents** (133 ms × 1.5–2.5 = 200–330 ms) and its Red line (500 ms) at 100k (0.8–1.4 s). Scoped to one organization's rowid range, the same index answers a 5,000-document organization's worst query in an estimated 45–75 ms. The scope must be a rowid range or a per-organization table: a `binder IN (...)` filter on an unindexed column still walks and ranks every match in the deployment first. The benchmark's `rowid = doc_id × 1024 + passage_no` scheme gives per-document ranges for free and doubles as ADR 0007's passage cap; allocating document ids in per-organization blocks (or one FTS table per organization) gives the organization range. Passages also win twice: `snippet()` tokenizes ~250 bytes per passage row instead of ~18 KB per document row, and AND queries are faster at passage grain because fewer passages than documents hold both terms. Grouping hits by document, as ADR 0007 §6 requires, costs nothing extra (best passage per document via `GROUP BY rowid>>10` ran at the same 515 ms as plain passage top-10 at 100k).

If storage or CPU ever did force a retreat, the cheapest alternative measured was a document-grain index for ranking plus a JavaScript scan of only the top ten documents' stored text to find the passage: +0.1–3 ms per query and zero extra index bytes. It loses true bm25 at passage grain and native passage links, so it is a fallback, not the plan. Memory is a non-issue: the most common term's whole doclist is ~0.6–0.8 MB even at 100k documents, the benchmark process peaked at 82 MB RSS, and the index itself (70 MiB to 1 GiB) lives in the OS page cache, so a cold cache costs latency, not correctness.

## Embedding passages is ruled out; sections fit, and the backfill clock is the limit

Dense vectors do not compress the way postings do: every chunk costs a full vector whatever its length. At 384 dimensions a float32 vector is 1,536 bytes, int8 384 bytes, binary 48 bytes. Brute-force scanning in sqlite-vec runs about 590 ms per million 1,024-dim float vectors and ~92–101 ms per million with a binary coarse pass plus float rescoring, on an Apple M4 ([sqlite-vec PR #276](https://github.com/asg017/sqlite-vec/pull/276)); the author puts brute force's practical limit "in the 100's of thousands" of vectors ([sqlite-vec v0.1.0](https://alexgarcia.xyz/blog/2024/sqlite-vec-stable-release/index.html)). Scaling those rates by an **assumed 2–4×** for Graviton2 gives:

| Docs | Layout               | Vectors | float32 | int8   | bit    | Unscoped float32 scan (est.) | bit scan + rescore (est.) |
| ---- | -------------------- | ------- | ------- | ------ | ------ | ---------------------------- | ------------------------- |
| 10k  | Sections, ~8/doc     | 80k     | 123 MB  | 31 MB  | 3.8 MB | 36–72 ms                     | 12–32 ms                  |
| 25k  | Sections             | 200k    | 307 MB  | 77 MB  | 9.6 MB | 90–180 ms                    | 30–80 ms                  |
| 100k | Sections             | 800k    | 1.23 GB | 307 MB | 38 MB  | 360–720 ms                   | 120–320 ms                |
| 10k  | Passages, ~60–70/doc | 600k+   | 922 MB  | 230 MB | 29 MB  | 270–540 ms                   | 90–240 ms                 |
| 100k | Passages             | 6M+     | 9.2 GB  | 2.3 GB | 288 MB | 2.7–5.4 s                    | 0.9–2.4 s                 |

Passage-grain vectors fail already at 10,000 documents: nearly a gigabyte of float32 that brute force must read on every query, on a host whose RAM is shared with Gitea, and backfill compute 7× larger than sections for no proven gain. Sections are also what the retrieval literature favours. Chroma's study found 200–400-token chunks with no overlap at the top of the recall table and overlap lowering efficiency ([Chroma](https://www.trychroma.com/research/evaluating-chunking)); NVIDIA found page- or section-level chunking the most consistent across corpora, with 256–512-token chunks best for factoid questions ([NVIDIA](https://developer.nvidia.com/blog/finding-the-best-chunking-strategy-for-accurate-ai-responses/)). Policies have explicit headings, so the natural unit is one section, capped at 512 tokens with sub-splits on paragraph boundaries, prefixed with "Title › Section" (a free, deterministic cousin of the context Anthropic found cut retrieval failures by 35% ([Anthropic](https://www.anthropic.com/news/contextual-retrieval))). One vector per whole document is not an option for small models with a 512-token limit, and it blurs a 3,000-word policy's sections together. The passage ADR 0007 already indexes remains the jump target: rank sections by meaning, then find the passage inside the top few with the FTS5 passage rows already there.

Partitioning matters here exactly as it did for FTS5. A vec0 partition key restricts the scan to one value's vectors before any distance is computed ([vec0 docs](https://alexgarcia.xyz/sqlite-vec/features/vec0.html)), so a 2,000-document organization at section grain is 16k vectors, an estimated 3–15 ms in any format, regardless of the deployment's total. Quantization is the second lever: int8 keeps ~97% of retrieval quality and binary with float rescoring ~96% on a 1,024-dim model ([Hugging Face](https://huggingface.co/blog/embedding-quantization)), but a 384-dim model has less redundancy and will lose more, so treat those as upper bounds until measured. Matryoshka truncation costs far more (1,024→256 keeps 86% ([mixedbread](https://www.mixedbread.com/blog/binary-mrl))) and is the wrong lever for an already-small model. sqlite-vec's ANN indexes are alpha in v0.1.10; its DiskANN build was 121× slower than flat, 3.1× bigger on disk and fast only from a warm cache ([PR #278](https://github.com/asg017/sqlite-vec/pull/278)), which a 4 GiB shared host cannot promise. The library is still pre-v1 ([sqlite-vec](https://github.com/asg017/sqlite-vec)).

### The model: a 33M-parameter encoder at int8, in a sidecar

At the size that fits, bge-small-en-v1.5 (MIT) and snowflake-arctic-embed-s (Apache-2.0) are tied at the top: 51.68 and 51.98 MTEB retrieval, against 41.95 for all-MiniLM-L6-v2 ([arctic-embed-xs card](https://huggingface.co/Snowflake/snowflake-arctic-embed-xs)); granite-embedding-small-english-r2 matches them with an 8,192-token window at 47M parameters ([granite card](https://huggingface.co/ibm-granite/granite-embedding-small-english-r2)). bge-small's int8 ONNX file is **34 MB** ([Xenova ONNX files](https://huggingface.co/Xenova/bge-small-en-v1.5/tree/main/onnx)). Static embeddings run ~100× faster but score below BM25 on NanoBEIR (0.44–0.50 against BM25's 0.45 and bge-small's 0.63) ([HF static embeddings](https://huggingface.co/blog/static-embeddings)), so they add little next to FTS5. EmbeddingGemma-300m is the quality step up, but it costs ~5× bge-small's compute per token, ships under the Gemma terms rather than an open licence ([card](https://huggingface.co/google/embeddinggemma-300m)), and would take an estimated 13–36 days to backfill 100k documents on this host.

The runtime must be out of process. transformers.js on onnxruntime-node ships Linux ARM64 binaries ([npm](https://npmjs.com/package/onnxruntime-node)), but under Bun it has an intermittent `NAPI FATAL ERROR` crash path that would take down the API ([cortexkit PR #124](https://github.com/cortexkit/magic-context/pull/124)); the report is from macOS, and whether it reproduces on Linux ARM64 is unverified. A `llama-server --embedding` container with a Q8_0 GGUF, or a small Node child process, isolates that risk; set the thread count explicitly, since llama.cpp's pool ignores container CPU limits ([ThakiCloud](https://thakicloud.com/tech-blog/en/dev/llama-cpp-threads-batch-cgroup/)). Estimated footprint: 34 MB of weights, 50–150 MB of runtime, 50–100 MB of activations at batch 4–8 × 512 tokens, so **150–300 MB**, inside a 0.5–1 GiB budget but not free on a 4 GiB host. Graviton2 lacks the i8mm instructions ONNX Runtime's fast int8 kernels target, so expect only ~1.5–2.5× from int8 over fp32 ([AWS ML blog](https://aws.amazon.com/blogs/machine-learning/accelerate-nlp-inference-with-onnx-runtime-on-aws-graviton-processors/)).

### Throughput, time and money on the t4g.medium

From FLOP counts cross-checked against x86 and Raspberry Pi measurements (no Graviton benchmark exists), a bge-small-class int8 model should manage **750–1,900 tokens/s on both vCPUs** at full burst. A query of ~20–30 tokens embeds in an estimated 15–40 ms; republishing one policy (~4,600 tokens with headers) takes 2.5–6 s in the background. The corpus is ~46M, 115M and 460M tokens at 10k, 25k and 100k documents. A t4g.medium earns 24 CPU credits an hour, banks at most 576 and defaults to Unlimited mode ([AWS burstable docs](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-credits-baseline-concepts.html)); running both vCPUs flat out drains the bank in ~6 hours, after which Unlimited bills ~1.6 vCPU-hours of surplus per hour at a commonly cited $0.04 per vCPU-hour ([re:Post](https://repost.aws/ko/questions/QU3_rVJhlLT-q1Uqm-YnODTw/burstable-instance-surplus-cpu-credits-charge), unconfirmed against AWS's price list), about $0.064 an hour.

Hosted prices per million tokens: Titan Text Embeddings V2 $0.02 ([AWS](https://aws.amazon.com/blogs/machine-learning/get-started-with-amazon-titan-text-embeddings-v2-a-new-state-of-the-art-embeddings-model-on-amazon-bedrock/)), OpenAI text-embedding-3-small $0.02 ([OpenAI](https://developers.openai.com/api/docs/pricing)), voyage-4-lite $0.02 with 200M free tokens ([Voyage](https://docs.voyageai.com/docs/pricing)), Workers AI bge-small-en-v1.5 $0.020 and bge-m3 $0.012 ([Cloudflare](https://developers.cloudflare.com/workers-ai/platform/pricing/)). A dedicated c7g.medium runs ~$26.50 a month ([DoiT](https://www.doit.com/compute/spot/us-east-1/c7g.medium)), so an always-on embedding box costs more in a month than the API costs for the 100k corpus in a year; it only makes sense as a spot instance stopped after a backfill.

The dollars are trivial everywhere. What breaks is the rebuild. ADR 0004 allows a derived index only if it is rebuildable from Gitea from scratch, and ADR 0007 keeps `search.db` unbacked-up on that basis and turns Red when "a full rebuild no longer fits overnight". FTS5 rebuilds 100k documents in ~70–90 s on an M1 (an estimated 2–4 minutes on the t4g), but an on-host embedding rebuild misses "overnight" already at **~10,000 documents**. So the vector table needs its own answer: back up the vectors (they are cheap to store and keyed on blob SHA, so they stay correct-or-visibly-stale), embed only sections whose content hash changed, or do backfills off-host.

## Bedrock adds a purpose, not a subprocessor; everyone else adds 30 days

Bindersnap's DPA promises "at least 30 days' notice before adding or replacing a Subprocessor" with an objection right and a pro-rated refund remedy (`apps/legal/documents/dpa.md`), and the subprocessors page says it uses each company "only for what's listed here" (`apps/legal/documents/subprocessors.md`). Bedrock keeps the text with AWS, already the host, in us-east-1: AWS commits that inputs are not used to train models and are "not shared with any model providers" ([Bedrock FAQs](https://aws.amazon.com/bedrock/faqs/)), and model providers have no access to Bedrock's deployment accounts or logs ([Bedrock data protection](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)). It needs a new line in the AWS row ("converts document text into search vectors"), an IAM grant in `infra/`, and a model ID pinned to us-east-1, avoiding `global.` and `us.` cross-region inference profiles that would widen the location column. Whether repurposing an existing subprocessor triggers the 30-day clause is a legal judgment; a `legal-reviewer` pass should settle it, and a courtesy notice is cheap.

Workers AI is the same legal entity as an existing subprocessor but a different role. Cloudflare does not train on or retain Workers AI content ([Cloudflare data usage](https://developers.cloudflare.com/workers-ai/platform/data-usage/)), but today the page says Cloudflare sees customer content only in transit, and nothing found guarantees US-only inference; it also strains ADR 0006, which keeps customer content off Cloudflare compute. OpenAI, Voyage, Cohere direct and Jina are each a new subprocessor with the full 30-day notice; OpenAI also keeps abuse-monitoring logs up to 30 days unless Zero Data Retention is approved, and US residency requires a sales contact ([OpenAI: your data](https://developers.openai.com/api/docs/guides/your-data)). No patient data means no BAA is needed, and Bindersnap should not reach for Bedrock's HIPAA eligibility in its copy. Whichever path is chosen, treat vectors as customer content: they are derived from the text and partly invertible, so they belong in the same deletion and export scope as `search.db`.

## Recommended design, with the line where each choice breaks

Build FTS5 at passage grain exactly as ADR 0007 describes, with these settings: `detail=full`, unicode61 with porter, one indexed column, text stored so `snippet()` and `highlight()` work, titles in a separate table, no prefix index until type-ahead needs one, and rowids allocated in per-organization blocks of `doc_id × 1024 + passage` so every query is a range scan from the start rather than an Amber retrofit. Add the synonym list next; the evidence favours it. BM25 is "a robust baseline" that dense retrievers often fail to beat out of domain ([BEIR](https://arxiv.org/abs/2104.08663)), and policy queries are full of exact terms, citations and acronyms where it is strongest. Write the semantic-search ADR only when ~40 labelled queries, the number Elastic found needed to tune past RRF ([Elastic](https://www.elastic.co/search-labs/blog/improving-information-retrieval-elastic-stack-hybrid)), show hybrid beating BM25 plus synonyms. When it is built: heading-aware sections ≤512 tokens with a title path and no overlap; Titan V2 on Bedrock for both documents and queries, falling back to FTS-only when Bedrock fails, or bge-small/arctic-embed-s int8 in a sidecar if legal review rejects Bedrock or its round trip is too slow; vectors in sqlite-vec `vec0` inside `search.db` with an `org_id` partition key, float32 while it fits, binary plus float rescore past that; fused with FTS5 by reciprocal rank fusion with k=60, which Elastic found "either better or similar to BM25 alone" on every BEIR set it tested, after collapsing both legs to documents by best rank. A MiniLM-L6 cross-encoder over the top 50 (estimated 50–200 ms on one core) is the last step, and bge-reranker-v2-m3 is too heavy for this CPU.

## Conclusion

The question ADR 0007 deferred, "memory it does not have", turns out to be the wrong constraint. A small encoder and section-grain vectors fit in a few hundred megabytes, and the storage and dollars are rounding errors at 100,000 documents. The binding constraint is CPU time against the derived-index rule: a lexical index rebuilds in minutes, a semantic one in days, so semantic search changes what "rebuildable" must mean before it changes the hardware. That shifts the decision from "can the host run a model" to "where do rebuilds happen and are vectors backed up", and it makes Bedrock attractive less for its price than for turning a multi-day job into a ten-dollar, hour-scale one under a subprocessor Bindersnap already has.

The second lesson is that one design decision protects both legs: allocating rowids and vector partitions per organization. It keeps FTS5's passage design inside its budget to 100k documents and keeps vector scans proportional to the searcher's own library. Build it in the first version of `search.db`, not as an Amber fix, and the thresholds that matter become the size of the largest customer, not the size of the deployment.
